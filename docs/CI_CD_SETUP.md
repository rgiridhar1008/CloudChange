# CI/CD Setup with CloudChange

CloudChange ships two equivalent pipelines: **GitHub Actions** (`.github/workflows/ci-cd.yml`) and **GitLab CI** (`.gitlab-ci.yml`). Both use **Trivy** for security scanning and the CloudChange Risk Engine to decide the deployment strategy.

## Pipeline stages

| # | Stage | What it does |
|---|-------|--------------|
| 1 | Test | `pytest` for the backend, `npm ci && npm run build` for the frontend |
| 2 | Trivy repo scan | Dependencies (`requirements.txt`, `package-lock.json`), hardcoded secrets, and IaC misconfigurations in `k8s/`, `helm/`, Dockerfiles |
| 3 | Docker build | Builds `backend` and `frontend` images (GitLab also pushes them to its registry) |
| 4 | Trivy image scan | Scans each image; fails on CRITICAL/HIGH (unfixed CVEs ignored) |
| 5 | Helm validation | `helm lint` and `helm template` |
| 6 | CloudChange analysis | `scripts/run_cloudchange_analysis.sh` runs the risk engine and deployment advisor |
| 7 | Deploy decision | Manual approval when `requires_approval` is true, automatic otherwise |

## Trivy files

- `trivy.yaml` – shared settings (severity, scanners, skipped dirs). Local use: `trivy --config trivy.yaml image cloudchange-backend:latest`
- `.trivyignore` – accepted findings (add a reason and an expiry for each)

The IaC scan is report-only for now. Change `exit-code` to `"1"` (GitHub) or `--exit-code 1` (GitLab) once existing findings are fixed.

## GitHub setup

1. **Environments** (`Settings -> Environments`): `development` (no rules) and `production-approval` (enable *Required reviewers*).
2. **Code scanning** (optional): SARIF upload works on public repos or with GitHub Advanced Security. Otherwise the upload step is skipped without failing the build.
3. Pin `aquasecurity/trivy-action` to a commit SHA for supply-chain safety.

## GitLab setup

1. **Container registry** must be enabled; the pipeline uses the built-in `CI_REGISTRY_*` variables, so no secrets are needed.
2. **Environments**: `production-approval` can be protected under `Settings -> CI/CD -> Protected environments` to restrict who can approve.
3. The deploy step runs as a **child pipeline** generated by `scripts/gitlab_deploy_pipeline.py`, so the manual gate only appears when the risk engine requires approval.
4. Container scanning results appear in the merge request security widget on GitLab Ultimate; on other tiers use the downloadable job artifacts.

minikube start
